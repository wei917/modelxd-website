## The five surfaces

- **XDuel** `/xduel` — free front door. One prompt, two anonymous models, vote
  blind → reveal price → vote again. Daily quota per mode. No web search here
  by design.
- **XCreate** `/xcreate` — paid studio, up to 4 models side by side. Text /
  image / video plus recipes (image_to_video, reference_frames,
  start_end_frames, video_edit). Per-seat thinking level + web search.
- **XTalk** `/xtalk` — multi-model rooms. Two templates: **Discussion** (2–8
  models, speaking order in-order / auto-bid / manual pick, per-seat
  character) and **Werewolf** (fixed 7-player board, server-held state).
- **XVote** `/xvote` — judge other people's duels; feeds the same ratings.
- **XBoard** `/xboard` — leaderboard by XD Score.

## Rating pipeline (`lib/xdrating.ts`)

Bradley-Terry, `BASE_RATING=1000`, `PRIOR_MATCHES=2`, 50 iterations,
`rating = 1000 + 400·log10(strength)`. Pools partition
`model_ratings` / `model_pairwise_wins` / `model_vote_stats` by mode:

- `MODES = text | image | video`, plus aggregate `all`
- `SEARCH_MODES = text_search` — search-on runs only (mixed-search runs
  contribute to neither pool)
- `GAME_MODES = werewolf` — quality-only (no value/stickiness), team outcome
  decomposed into winner×loser pairwise events; **excluded from `all`**

## XTalk Werewolf specifics

Server holds the game (`app/api/xtalk/werewolf/route.ts`); the client knows
nothing and just renders what comes back — that is the only reason a human can
sit at the table honestly. One act per request; the client loops.

- Board: 2 wolves, 1 seer, 1 doctor, 3 villagers. `minPlayers = maxPlayers = 7`.
- Night order is wolf → seer → doctor → dawn, so the **doctor acts after the
  wolves have chosen**; a correct protect produces a quiet morning.
- Every living player speaks once per day in a rotating `turn_order`. There is
  **no speaking-credit economy here** — that exists only in Discussion's
  bid mode (`WALLET_START=6 / REGEN=2 / CAP=8`).
- Per-model call timeout is **90s** (`MODEL_TIMEOUT_MS`), one retry for an
  empty reply, no retry after a timeout. Timeouts become visible ⚠ abstentions,
  never silent skips.
- `askModel()` field extraction is a SECURITY boundary: a reply that looks
  structured but yields no clean field is DROPPED, never printed raw, because
  the raw text contains the model's private `reasoning`. (A human doctor once
  saw a wolf's whole plan through this path.)
- Same model may take several chairs; duplicates get "name (2)", "name (3)".

## Per-feature model availability (new)

`ai_models.blocked_features text[]` + `lib/model-features.ts`. A model carries
the feature keys it must NOT be offered for. Keys in use: `xtalk_werewolf`,
`xtalk_discussion`, `xduel`, `xcreate`.

Enforced in three places so a stale tab cannot slip past: the picker
(`ModelPickerDialog` takes `feature=`), the surface's own model list
(`allowedFor(models, FEATURE.x)`), and the API (werewolf create REFUSES rather
than filtering — silently seating 6 at a 7-seat table deals the wrong board).

Current rule: **Kimi K3 blocked from Werewolf** (~26 tok/s with a large default
reasoning budget, measured 75s+/turn against the 90s ceiling; its timeouts were
changing who got lynched). Still fully available everywhere else.

Blocking a model is a DATA change, not a deploy:
```sql
update ai_models set blocked_features = blocked_features || '{xtalk_discussion}'
 where model_name = 'some-model';
```
NOTE: Discussion's picker does not yet pass a `feature` key — storing an
`xtalk_discussion` block would not be enforced until that one line is wired.

## Site agent (new)

`/api/agent/ask` + `content/site-guide.md`. Answers questions about the SITE
(what it is, where a feature lives, what it costs) and returns an optional
route from an allow-list so a hallucinated path can never become a dead link.
Claude Haiku, no tools, never generates, never bills the user.

- **The owner pays**, not the user — no `debitCredits` call. Uses the same
  `ANTHROPIC_API_KEY` as XDirector.
- Public + unauthenticated by necessity → basic in-memory rate limit
  (12/min/IP). This is a floor, not a wall: per serverless instance. **Move to
  a shared store before real traffic.**
- `content/site-guide.md` is its ONLY knowledge of the product. A stale line
  there becomes a confident wrong answer — update it when features move.

Two front ends, one API:
- `LandingAgent.tsx` — landing page middle. **Fixed-height** panel (310px)
  ABOVE the input so answering never reflows the page; prefilled with an intro
  that is the agent's real first turn; multi-turn; persists in `sessionStorage`
  (survives navigating away and Back) with a Start-over button.
- `Omnibox.tsx` — ⌘K palette + sticky bar on app surfaces only (allow-list of
  routes; NOT on the landing/marketing pages). Searches pages, models, your
  generations, your XTalk rooms. Never guesses search-vs-ask: the agent is an
  explicit pinned last row, so an ambiguous keystroke cannot spend money.

## Decisions taken (don't re-litigate without new information)

- **Apple + LINE sign-in: dropped for now.** Desktop OS share in TW/JP is
  ~81%/76% Windows, so the iPhone-majority argument does not apply to a
  desktop product; Sign in with Apple on Windows is worse than Google, and
  costs $99/yr plus a 6-month secret rotation. If a mobile push ever happens,
  LINE is the higher-value one for these markets (LINE is ~94% penetration in
  TW), and it needs a custom OAuth bridge — Supabase has no LINE provider.
- **Werewolf ratings stay out of `all`** — social deduction is not the skill
  the duels measure.
- **HappyHorse 1.0 ranks above 1.1** on the board and that is not a bug: 1.0
  follows prompt instructions (e.g. shallow DoF) more faithfully while 1.1
  optimises for scene detail and runs slower for the same price.
